## Decisions on the report's open points

- **Leap seconds.** `BYSECOND=60` is accepted (RFC 5545 allows it) but never
  matches, because neither JavaScript nor Dart dates can represent it. A rule
  whose only BYSECOND value is 60 has no occurrences. Previously it rolled
  into the next minute.
- **Oracle independence.** `tools/verify/oracle.mjs` is a brute-force
  evaluator written from the RFCs. It uses its own calendar arithmetic, finds
  week 1 as the week containing January 4, and shares no code or masks with
  either package. It is now the primary check, run in CI on every change for
  the corpus and for fresh fuzz cases. It confirms all 7,408 corpus cases in
  its scope (DAILY to YEARLY with every BY* part, BYSETPOS and SKIP). After
  the recheck it no longer emits period by period: it collects all
  candidates and orders them before DTSTART, UNTIL, COUNT and the query
  apply (it had shared F01's shortcut), and covers SKIP with nth BYDAY. The
  remaining 1,004 sub-daily cases are checked against python-dateutil, whose
  "spins on an empty rule" cases stay reported separately.
- **CI trigger.** The `verify` job now runs on every push and pull request.
- **JSCalendar DTSTART and COUNT** (RFC 8984: the start is always the first
  occurrence). This belongs to the caller. Mobile's recurrence code should be
  audited separately; the engine is unchanged here.
- **DST gaps and folds.** These stay with the adapter and its caller. The
  engine is floating by design.
- **Validation policy.** Values outside RFC 5545's ranges are rejected.
  Combinations RFC 5545 forbids but rrule.js evaluates (BYWEEKNO with
  non-YEARLY frequencies, for example) are still evaluated, for compatibility.

## Recheck of c587aa4

A second review checked the pushed fixes and reported six issues (F01–F06),
with reproduction scripts. All six reproduced exactly (12 TS and 5 Dart
failures) before any change. The expected results were checked against
RFC 7529 section 4.1 and RFC 8984 section 4.3.3.1 (invalid days are adjusted
before BYDAY and BYSETPOS; SKIP removes dates already produced, not every
date earlier than the last one) and pinned by hand, not regenerated from
either engine.

| ID | Verdict | Cause | Fix | Pinned by |
|---|---|---|---|---|
| F01 SKIP=FORWARD drops distinct dates when periods overlap | valid (both) | a moved date (Feb 31 18:00 → Mar 1 18:00) was emitted with February, and March's earlier Mar 1 09:00 was then dropped as `<= lastEmitted`; UNTIL and query bounds stopped at the spill | MONTHLY SKIP=FORWARD rules defer only the dates moved into the next month and merge them in order with that month's dates as these are generated; exact duplicates once. Other rules keep the plain loop. (The first version buffered whole periods: see G02.) | 8 hand-checked cases in `regressions.json` (all/after/before/between, UNTIL and COUNT inside the overlap, positive and negative positions, a date selected by both periods); `skip-overlap.json`; Dart `iterate` tests |
| F02 set serialization loses value domains | valid (TS) | `toString()` wrote every RDATE/EXDATE with the set's TZID | one property line per domain: UTC values with `Z`, each explicit TZID, values following the set | `test/recheck-fixes.test.ts` |
| F03 mixed-domain RDATEs queried in raw order | valid (TS) | RDATEs were sorted by raw fields, converted one at a time, and the loop stopped at the first value past a bound | values are converted and sorted as instants before they meet the bounds (on every query, so adapter changes apply) | `test/recheck-fixes.test.ts` (every query, fresh sets, cache on and off, both input orders) |
| F04 equal raw values in different domains collapsed | valid (TS) | `_addDate` de-duplicated by raw milliseconds | de-duplication by (raw value, domain); equal instants are still emitted once | `test/recheck-fixes.test.ts` (RDATE and EXDATE, both orders, adapter change) |
| F05 callback expansion not bounded by demand | valid (TS) | doubling time windows reached a SECONDLY rule after a year-old RDATE with a window of months, materialized before the callback ran (out of memory at 64 MB) | lazy merge: each RRULE/EXRULE is a stream refilled in batches that stop after N dates (N doubles up to 65,536), resuming after the last one; EXRULEs seek to the candidate (G01) | subprocess tests under a 64 MB heap for `all` and `between`; order, exclusion and equivalence tests |
| F06 nth BYDAY of a moved date checked in the source month | valid (both) | the moved May 1 was looked up in April's nth-weekday mask | a date moved FORWARD is checked against the nth weekdays of the month it lands in (MONTHLY, or YEARLY with BYMONTH; YEARLY ordinals count in the year, which the move never leaves) | 5 hand-checked cases in `regressions.json` (positive, negative, YEARLY+BYMONTH, BACKWARD control, BYSETPOS after the move); `skip-overlap.json` |

The oracle had F01's shortcut too and excluded SKIP with nth BYDAY. It now
collects all candidates before ordering them, checks a moved date as a date
of its own, and agrees with the hand-checked cases. `skip-overlap.json`
(1,000 cases, also part of every fuzz batch) targets these combinations; 13
of its cases fail on `c587aa4`. Performance is unchanged within measurement
noise in both packages.

Not changed: an RDATE/EXDATE with `VALUE=DATE` is still midnight in the
set's zone (as in rrule.js) and is serialized as a date-time with the same
meaning.

## Second recheck of ab8b4f3

A third review checked `ab8b4f3` and found two memory failures and one
oracle bug (G01–G03). All six failing probes reproduced before any change.
Another oracle gap (G04) turned up in the fresh fuzz run afterwards.

| ID | Verdict | Cause | Fix | Pinned by |
|---|---|---|---|---|
| G01 dense EXRULE exhausts memory in callback queries | valid (TS) | the EXRULE stream was advanced date by date to each candidate, with batches that doubled without limit: a SECONDLY EXRULE a year before the first candidate ran out of memory at 64 MB | an EXRULE stream seeks: when its batch runs out, the next one starts at the candidate being tested, so skipped exclusions are never stored; every rule batch is capped at 65,536 dates | 64 MB subprocess tests: dense EXRULE, callback rejecting its first result, a dense RRULE fully excluded by a dense EXRULE |
| G02 SKIP buffering materializes a whole period | valid, regression of F01 (both) | every SKIP rule buffered and sorted its whole period before emitting: 31.6 million numbers for a YEARLY rule with every second, even with COUNT=1 | only MONTHLY SKIP=FORWARD defers anything, and only the dates moved into the next month (at most one day's times); everything else is emitted as generated. BACKWARD and YEARLY never leave their period. | 64 MB subprocess tests in TS and in a Dart child VM: YEARLY and MONTHLY, OMIT/BACKWARD/FORWARD, COUNT=1, after(), callback and `take` limits |
| G03 oracle stopped a limited between() before its window | valid (tooling) | the early stop compared min(COUNT, limit) with all candidates since DTSTART, including those before the window | the global COUNT and the query limit are tracked separately; only candidates inside the window count towards the limit | `tools/verify/oracle.test.mjs` (hand-checked; run by CI) |
| **G04** oracle truncated at its search horizon | **new** (tooling) | the oracle searched 300 years: a fuzz case whose 20th date is in 2342 got 19 dates and disagreed with the (correct) engines | the horizon is 400 × INTERVAL years (one full Gregorian cycle of period contexts, so an empty search proves an empty rule); a productive rule still unsettled at the horizon is out of scope instead of truncated | `tools/verify/oracle.test.mjs` |

Resource guarantees as implemented: rule expansion holds at most one batch
(65,536 dates) per rule plus the dates returned; SKIP rules hold at most one
day of moved dates. CPU is not bounded by the result size: a query still
walks every period from DTSTART, as in rrule.js (for example, an EXRULE
starting a year earlier is walked once per batch refill).
